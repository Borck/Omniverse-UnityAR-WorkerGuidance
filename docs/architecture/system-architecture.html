System Architecture — Omniverse → Unity AR

A Digital Twin for step-driven assembly guidance

A layered OpenUSD scene on Omniverse Nucleus is the single source of truth. A Python server derives per-step delivery artifacts and serves them to a content-free Unity 6 runtime on Vuzix smart glasses — over one small control channel and one immutable, content-addressed data channel.

Source Omniverse / Nucleus (OpenUSD) Server FastAPI + gRPC + Kit Client Unity 6 · Vuzix M4000 gRPC :50051 HTTP :8080

Central thesis

A change to the authoritative USD scene propagates deterministically and automatically to the AR consumer — “saving in Omniverse updates the worker’s view within ~60 s” — while the consumer stays a stateless, content-free renderer whose only inputs are an immutable asset stream and a small deterministic control channel.

01 Architectural style

Two channels with different physics

The primary architectural decision is a control / data-plane split. The control channel stays small and analysable — a state machine over a handful of message types. Large binary payloads travel a separate channel built for throughput and caching. The two planes meet at exactly one point: an immutable content hash.

Control plane

Session & step orchestration

  • Carries session lifecycle, step activation, confirmations, live-sync notifications
  • Transport gRPC bidirectional stream (HTTP/2); REST bridge fallback
  • Shape small, frequent, ordered per session
  • Semantics deterministic · idempotent

GuidanceSessionService · GuidanceControlService

asset_version =

Data plane

Asset delivery

  • Carries GLB geometry + animation, Vuforia Model Target databases
  • Transport gRPC server-streaming (chunked) + HTTP file serving
  • Shape large, occasional
  • Semantics immutable · content-addressed · cacheable

AssetTransferService · /api/assets · /api/targets

Identical content ⇒ identical version ⇒ no re-transfer and no re-render. The system is self-deduplicating: a save that produces byte-identical geometry is correctly silent.

02 Design principles

Six commitments, each enforced in code

P1

Single source of truth

Omniverse / Nucleus owns geometry, animation, and layer semantics. The server derives; it never authors. The client renders; it never stores.

P2

Zero embedded assembly data

No .glb, .dat, .xml, or manifest ships in the app. A Unity build gate (NoEmbeddedAssemblyDataCheck.cs) fails the build if any is found.

P3

Determinism

Same USD inputs ⇒ same ResolvedStep and same cache_key every run. Steps totally ordered by (sequence, step_id).

P4

Immutability & content addressing

Versions are SHA-256 of the bytes actually served — hashed after mesh slimming, so the version reflects the delivered payload.

P5

Idempotency

Duplicate StepCompleted / heartbeat messages are absorbed by a dedup set. Reconnect restores the last job and step, never resets.

P6

One active model

Exactly one GLB instance under one root transform at any instant; presenting a new step disposes the previous one. Bounds memory and heat on the wearable.

03 The Digital Twin loop

Two halves joined by one shared file

The system splits into an Omniverse half that derives delivery artifacts from USD and a delivery half that pushes change to the device. They are joined by a single contract boundary: shared/samples/manifests/<job_id>.manifest.json. The whole loop pivots on that file.

Why watcher lives outside Kit

The sync loop runs whether or not an interactive Kit session is open — the artist controls Kit independently.

Why incremental rebuild

Single-part edits showed ~80% of rebuild time re-doing unchanged parts. Changed URLs are filtered via an env var.

Why slim-before-hash

Stripping unused vertex attributes before hashing makes asset_version reflect the exact bytes served.

Why content hashing

Automatic dedup: identical bytes ⇒ unchanged manifest ⇒ no broadcast ⇒ no client work. Self-correcting.

08 Data transfer

Who moves what — HTTP vs gRPC

FastAPI is not a third transport — FastAPI is HTTP. It is a web framework running under uvicorn, so "served by FastAPI" means "served over HTTP." The system therefore has exactly two transports, running as two separate server processes on two ports. gRPC does not run through FastAPI.

The per-payload mapping

The heavy binary payloads are moved by gRPC, not FastAPI. FastAPI's job in the runtime path is to serve the small manifest — the lookup table mapping each asset_version to a concrete file name. The control channel names a version, the manifest resolves it to a file, gRPC streams the bytes.

How gRPC streams a file — 64 KB chunks

gRPC does not send a file as one blob. StreamStepAsset is a server-streaming RPC: the server opens the file and yields it as an ordered sequence of StepAssetChunk messages of 64 KB each. A 2 MB GLB becomes ~32 chunks; the client reassembles them by chunk_index until is_last, then writes the file into its version-keyed cache.

# grpc_asset_service.py — the core streaming loop (chunk_size = 64 * 1024)
with stream_path.open("rb") as handle:
    chunk_index = 0
    while True:
        data = handle.read(self._chunk_size)      # 64 KB
        if not data: break
        is_last = handle.tell() >= total_size
        yield guidance_pb2.StepAssetChunk(
            asset_version=asset_version,           # which version these bytes are
            chunk_index=chunk_index,               # ordering key
            data=data,                             # the raw bytes
            is_last=is_last,                       # end-of-stream marker
        )
        chunk_index += 1

HTTP alternative

FastAPI also serves /api/assets/{ver}/{file} and /api/targets/{ver}/{file} as immutable FileResponses — the manifest URLs point here. Bytes can travel over HTTP; the current runtime path uses gRPC streaming, with HTTP as the fallback route.

Why the split

Small decision-carrying data (control, manifest) fit request/response. Large payloads use gRPC server-streaming in 64 KB chunks, so the device never buffers a whole file, transfer is backpressured over HTTP/2, and it reuses the session's open connection.

09 Non-functional properties

Invariants and how they are achieved

Determinism
Total step ordering; canonical-JSON SHA-256 cache_key over all resolver inputs — layer_stack_resolver.py
Idempotency
Dedup sets keyed by (job, step, ts); register-or-resume sessions — grpc_session_service.py
Immutability
Content-addressed asset_version; Cache-Control: immutable on /api/assets and /api/targets
Bounded device
One active model; dispose-before-present; one active target — bounds memory and thermals on the wearable
Resilience
Periodic heartbeat + reconnect; frozen-step with cached asset during network loss; session resume
Bandwidth economy
Slim-before-hash; content dedup; optional Draco; incremental rebuild of only changed parts
Observability
Structured JSON logs with fixed fields timestamp · level · event · session_id · step_id · correlation_id
No embedded data
Editor build gate rejects any embedded assembly file — NoEmbeddedAssemblyDataCheck.cs
